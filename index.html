Task generator

Turns one compliance control and a client inventory into scoped, per-asset audit tasks.

BusinessAICoreKafkaBedrockStrandsPython
01Business pain point

A platform has to decide how many audit tasks each control becomes, and for which systems. MFA across three platforms is three tasks. Thirty-seven vendors might be thirty-seven. A missing technology is zero. An auditor made that call by hand and it ate a week.

  • BusinessOver-generation is client busywork. Under-generation is a missed audit finding. Being wrong costs money in both directions.
  • BusinessVolume: hundreds of controls per tenant, with new tenants onboarding on banking, ISO 27001 and SOC 2 standards.
02Current solution

Deterministic rule engines plus prompts. A self-audit I ran found a split rulebook. Prompts described one version of the rules and code enforced an older one, with 58k to 76k token system prompts on hard controls.

  • AIAccuracy around 60%. Identical inputs produced 6, then 17, then 6 tasks.
  • AICoreThe audit found invented "ground truth" labels, a three-way authority conflict, accuracy measured circularly, and a delivery layer that shipped suppressed rows as normal tasks.
  • CoreAll 12 frequency-engine tests were failing and nobody had noticed.
03My proposal
  • BusinessAIDiagnose before designing. A three-agent read of the code, spot-checked by me, showed the 60% was not a model problem. That ruled out a model-swap detour.
  • BusinessKill my own design. I wrote up an applicability gate in June, then deleted it before it shipped once the agentic route made it redundant.
  • AIGive the agent every decision. Rule engines become advisory tools it may overrule, and rules become prose skills.
  • AIOne precedence order in every prompt: requirement text, then a frozen human decision record, then rule defaults, then agent judgement. Forbidden reasoning is spelled out by example.
  • BusinessAsk humans once. A questioner agent asks clarifying questions per tenant batch and the answers freeze into a record.
04Architecture

Failure modes and failsafes

LayerFailure modeFailsafe
KafkaWorker crashes mid-batchStatus is saved as processing before work starts. A replayed batch found in processing is treated as a crashed attempt and resumed, not ignored. Background recovery loops republish unpublished questions and resume unanswered batches.
KafkaTwo messages from one tenant race the check-then-actA per-tenant intake lock serialises the gate. Before it, both messages saw "no batch", both created one, and the second save silently dropped the first.
KafkaRestart replays already-published controlsEach control publishes its own response, so a naive restart duplicates. Procedure: trim the batch against the journal's publish-acknowledged lines first. Consumer offsets are handled with explicit tooling, not auto-commit.
ProcessService dies and stays deadRestart policies on every worker unit plus an offset-skip guard. Before this, a dead worker cost 4 to 6 days of QA downtime and ~226 requests aged out of retention.
KafkaUpstream sends a wrong total_controlsKnown tradeoff: a count that is too high stalls the batch. Documented as a hard dependency in the runbook, with a manual trim-and-resume path.
AIQuestions go unanswered or contradictUnanswered questions take their stated default with a flag recorded. Contradictions resolve the recall-safe way with a flag. If the freeze step fails, a mechanical merge runs as fallback.
AIAgent invents a system or vendorIt may only use names that exist in the declared environment. Scope decisions must quote a listed marker verbatim or take the default branch.
AIReviewer finds a faultThe reviewer names a check id and the owning agent, and only that stage re-runs. Re-reviews are delta reviews. Two failed cycles route the control to human review instead of looping.
AIDaily token quota exhaustedModel tier is a config flip plus restart. Batches of 227, 122 and 150 controls ran on cheaper tiers with zero throttles.
DataRules drift between prompts and codeRule profiles are versioned, SHA-256 sealed and loaded fail-closed, so a tampered or missing profile stops the run.
Models
Opus 4.5 for questioner and planner, Sonnet 4.6 for classify, scope and review, Haiku 4.5 to author, GLM-5 for the test-procedure worker. Retiered under quota in July.
Rulebook
19 scope patterns on two axes, nine multiplicity rules, six suppression rules. Each task carries a provenance field the reviewer checks against the record.
Caching
Five-minute prompt cache TTL (writes 1.25× against 2× at one hour). Section-scoped reference reads, because a whole-file read costs 10 to 20×.
  • CoreKafka: a request topic in, a response topic out, and a second consumer group for the follow-up loop sharing one durable batch store. 10 topics across 5 worker types.
  • CoreTenant batch gating: controls accumulate until the batch is complete. Two messages from one tenant could race a check-then-act and silently drop a batch, so a per-tenant intake lock guards it.
  • CoreCrash-safe transitions: status is saved as processing before work starts and restored on exception so a Kafka replay resumes. A batch found already processing is treated as a crashed attempt.
  • CoreBackpressure: a thread pool behind a bounded semaphore so the queue can never outgrow its slots.
  • CoreDurability grew from one file-locked JSON to per-control checkpoints with background recovery loops. Rule profiles are versioned and hash-sealed, and load fail-closed.
  • AIPer-stage model tiering chosen against quota as well as capability.

Evidence mapper

Maps audit tasks to the evidence files that satisfy them, then writes the finding.

BusinessAICoreKafkaBedrockStrandsQdrantS3
01Business pain point

Every audit task needs the right evidence file, found among thousands of policies, screenshots, exports and spreadsheets. It is the slowest step of an audit.

  • BusinessA wrong "compliant" claim is worse than an honest gap, so both precision and recall matter.
  • BusinessHundreds of tasks per audit, per tenant, with the reviewer needing to trust the mapping enough not to redo it.
02Current solution

Four retrieval architectures behind one config flag over a shared result type: a multi-agent auditor, a sketches DAG, GraphRAG (built twice) and a set-based retriever.

  • AIThree parallel reviewers each graded the stack B minus. Every defect was silent wrongness.
  • AIGraphRAG's first graph had 110 nodes for 100 documents, hit@6 of 40% and recall@6 of 16.5%. A deeper rebuild matched the simple retriever at 7× the latency.
  • AIThe retriever's verifier saw only ~500-character snippets, so it claimed topically related files. 52 claims in the bench were wrong.
03My proposal
  • BusinessKill GraphRAG as a retriever. Same quality as the simple engine at seven times the latency is not a trade.
  • AIBet on an agent that reads file contents with four tools, against my own prior and two frontier-model reviews that argued against it on cost, vocabulary mismatch and injection.
  • BusinessAIDecide by blind bench, not opinion: outputs frozen at a commit, engine labels randomised, ten fresh reviewers, sealed key. Then reverse the architecture.
  • BusinessAccept the price: about 12× latency and 15 to 25× marginal cost, because the old engine made false claims.
  • CoreProduction shape is an in-process loop that reproduces what was benchmarked. A per-task subagent harness would have meant 30 Node processes at 150 to 300 MB each.

Vendor-risk platform

A vendor-risk backend and an AI service that drafts and judges answers with cited evidence.

BusinessAICorePostgresKafka / RedpandaKubernetesTextractBedrock
01Business pain point

Assessing a vendor means reading a SOC 2 report, around fifty policy PDFs and 147 screenshots, then answering a questionnaire with cited proof. One tenant manages thousands of vendors.

  • BusinessA reviewer cannot read that much per vendor at that scale.
  • AINaive automation risks confident answers with hallucinated citations, which is worse than no automation in an audit.
02Current solution

A legacy vendor module with manual questionnaires and a login service that returned errors for vendor accounts. My first AI pass was a one-shot evaluator over parsed text.

  • AIIt cited zero images across 12 test questions.
  • AIIt missed a certificate and an audit report that were in the evidence pack.
03My proposal
  • BusinessKeep the product deterministic and make AI a bounded advisor. A domain layer with scoring, tiers and state machines imports only the standard library, so it cannot call a model.
  • AIThe AI emits a verdict, a confidence and citations. A human review decision ratifies it. Escalation fires on a marker the model emits, not on a score.
  • BusinessTwo generations from one lineage: a full backend (workflow, portal, AI), then a Kafka-only AI service that writes findings into each tenant's own database and never touches the workflow owner's tables.
  • AIPort the evidence-reading harness from the mapper and add citation verification: verbatim span match, else at least 0.8 token overlap.
  • BusinessAIBuild the evaluation harness first: a 97-case golden set so every change is measured.

  • CoreDelivery: the service runs on Kubernetes through CI, ArgoCD and Helm. The backend runs under systemd behind nginx.
  • AIFive deterministic guards after the model: reviewer-instruction quarantine, recency, not-applicable, non-probative citation and calibration.

Script builder

Generates, tests and runs evidence-collection scripts against live client cloud accounts, then replays them for free.

BusinessAICoreKafkaPostgresQdrantBedrockFastAPI
01Business pain point

Auditors hand-wrote bespoke evidence-collection scripts per client, hundreds of them, with no reuse. When an integration failed, the platform silently fell back to document-based AI, which is weaker evidence.

02Current solution

A library of 209 integrations across eight technologies and six standards. A May audit of the live system found real quality problems.

  • Core51 of 207 database rows differed from what was on disk.
  • CorePlaceholder text in 19 integrations, "dummy" or "test" language in 7, certificate verification switched off in 2, and one script with hardcoded terminated users.
03My proposal
  • BusinessGenerate a tested Python module from a plain-English control, run it against the client's live account, store it keyed by control, technology and standard, and replay it with zero model calls on every later audit.
  • AITwo agents only: research and codegen. Everything else is a gate the model cannot skip.
  • CoreIt is the only service that runs LLM-written code against customer credentials, so guardrails are never agent-optional.
  • BusinessDecouple what has one caller. A shared standards-mapping module had a single real user and two disagreeing code sets, so the service got its own copy with 14 canonical codes.

Failure modes and failsafes

KafkaPoison messageBoth consumers catch, log and commit past a malformed message so it cannot kill the loop.

Gate loop
Validate (AST check, import allowlist on both files), test gate (per-run venv, mock-only tests), execute (subprocess, credentials by file path, nonce-prefixed result, last match wins). One shared repair budget of 2.
Retry policy
Failure class drives it: auth, then code bug, then transient.
  • CoreThree front doors: HTTP generation, a Kafka generation topic, and a Kafka replay topic that skips generation. Results go to split success and failure topics.
  • CoreAt-least-once delivery: auto-commit off, commit after handling. A poison message is caught, logged and committed past so it cannot kill the loop.
  • CoreEvery fan-out isolates faults. One control failing cannot stop its siblings, and a batch-level timeout of 7,200 s bounds the whole run.
  • CoreThe registry lives in Postgres through asyncpg for the execution path, with a filesystem manifest for the CLI runner. Research results are cached in a vector store for 7 days and written only after the gates pass.
  • CoreA settings bug made every environment override do nothing. The code passed parsed YAML as init arguments, which outrank environment variables, and a cached settings object locked the wrong value in.
  • AIAn SDK introspection tool is ranked first in the source-conflict order, which stops invented API calls.

Honest ledger

What is finished, what is not, and what I would do differently.

A pitch that hides the rough edges is not worth the page. These are the ones I know about.

Status, stated plainly

  • Task generator is in production with real tenants. Its later branch work is newer than my notes.
  • The agentic evidence-mapping engine is proven in benchmarks but sits on a branch. Production main still runs the older engines behind a flag.
  • The Script builder consolidation is likewise unmerged.
  • The agentic vendor-risk evaluator exists but is off by default. The 10 of 97 golden cases that still fail are known.
  • Telemetry and metering are planned, not built.

What I would change

  • Secrets hygiene. Rotation lagged behind speed. I now track exposures in a risk register by type, and would gate commits on it from day one.
  • Test coverage was uneven: strong mocks in some services, near zero in the UI.
  • Documentation drifted from code. Notes now carry dates and say to trust the code.
  • Generated-code gates check that a script runs, not that it is audit-grade. Isolation is the next thing I would harden.
Lesson

Silent wrongness beats crashes as the failure mode. Zero mappings reported as success. A gate that dropped every response token. Look for those first.

Lesson

Config drift beat code correctness three times. The deployed code was right and the environment file was wrong.

Lesson

Measure before deciding. Two confident expert opinions lost to a blind test with fresh reviewers.
